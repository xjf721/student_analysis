# 教学过程智能分析与预警平台服务器部署设计

## 1. 目标与范围

本设计用于将当前 Flask + MySQL 项目快速、可靠地部署到一台可运行 Docker Compose 的 Linux 服务器。

已确认的环境与约束：

- 服务器可使用 Docker Compose，但拉取镜像需要配置可用的国内镜像源。
- 当前先通过服务器 IP 在校园网内访问，后续可能配置域名和 HTTPS。
- 服务器已有运行于 Docker 容器中的反向代理，本项目不重复部署入口服务。
- 首次上线使用空数据库，业务数据由教师在页面中重新导入。
- 部署包不得携带学生原始 Excel、上传文件、数据库数据、日志、密钥、Git 历史或备份文件。
- 本阶段为单机快速部署，不引入 Kubernetes、Redis、Celery 或多节点高可用。

## 2. 方案选择

采用 Docker Compose 管理 Web 和 MySQL 两个容器，并复用服务器现有的反向代理容器。

未选择的方案：

- Web 容器加宿主机 MySQL：数据库安装、配置、迁移和备份流程不统一。
- 全部直接安装在 Linux：环境复现和回滚速度较慢。
- 项目内再部署反向代理：与服务器现有能力重复，并增加冲突风险。

## 3. 总体架构

```text
校园网用户
    ↓
服务器现有反向代理容器
    ↓ 共享 Docker 网络
student-analysis-web:8000
    ↓ 项目内部 Docker 网络
student-analysis-db:3306
```

网络边界：

- Web 同时加入现有代理共享网络和项目内部网络。
- MySQL 只加入项目内部网络。
- Web 和 MySQL 均不发布宿主机端口。
- 反向代理通过 `http://student-analysis-web:8000` 访问应用。
- 共享网络名称通过 `.env` 中的 `PROXY_NETWORK` 配置，并在启动前验证。
- 反向代理继续负责校园网访问限制；后续增加域名和 HTTPS 时不改变应用架构。

## 4. 容器设计

### 4.1 Web 容器

- 使用固定版本的 Python slim 基础镜像和独立生产依赖清单。
- 使用非 root 用户运行 Gunicorn，监听容器内 `0.0.0.0:8000`。
- 初始配置为 2 个 worker、每个 worker 4 个 thread、超时 120 秒，均可通过环境变量覆盖。
- Docker 健康检查调用 `/health`。
- 设置 `restart: unless-stopped`、资源限制和日志轮转。
- 上传文件和辅助文件日志写入持久化卷，镜像本身无状态。

### 4.2 MySQL 容器

- 使用固定的 MySQL 8.x 镜像版本，不使用 `latest`。
- 使用 `utf8mb4` 字符集，数据目录使用命名卷持久化。
- 数据库密码、数据库名和业务用户由 `.env` 注入。
- 不映射 `3306` 到宿主机。
- Web 只能在数据库健康检查通过后执行初始化。

### 4.3 健康检查

新增 `/health` 接口。成功响应表示 Flask 能处理请求且数据库连接可用。健康响应不得泄露数据库地址、账号、异常堆栈或其他敏感配置。正常返回 HTTP 200；数据库不可用时返回 HTTP 503。

## 5. 生产配置整改

- 生产环境使用 `FLASK_ENV=prod`，禁止通过 `app.py` 的 `debug=True` 启动。
- `SECRET_KEY`、MySQL root 密码和业务密码不得提供可用于生产的代码默认值。
- 缺少关键密钥或仍使用示例值时，应用或部署脚本必须拒绝启动。
- 数据库初始化使用生产配置，不得通过开发配置创建表。
- 生产部署脚本不得调用 `init_database.py --reset`。
- 首版只支持新建空库和现有兼容字段初始化。后续数据库结构变更应引入 Flask-Migrate/Alembic。
- 外部 Excel 路径必须显式配置或仅从上传目录读取，不依赖开发机根目录的示例文件。

## 6. 交付物与安全导出

每次发布生成：

```text
student-analysis-release-<version>.tar.gz
student-analysis-release-<version>.tar.gz.sha256
```

压缩包包括应用源码、`Dockerfile`、`compose.yaml`、`requirements-prod.txt`、`.env.example`、`deploy.sh`、`backup.sh`、`restore.sh` 和 `DEPLOY.md`。

导出使用明确允许列表。以下内容不得进入发布包：

- `.git/`、`.agents/`、IDE 配置和缓存；
- `.env`、私钥、真实密码及其他密钥文件；
- `uploads/`、`logs/`、`export/`、`new-datas/`、`---bak---/`；
- 任意目录中的 `.xls`、`.xlsx` 原始业务文件；
- 现有压缩包、数据库转储、测试缓存、虚拟环境和 Python 缓存。

打包前执行敏感文件检查；发现 `.env`、Excel 业务文件、数据库转储或私钥进入待打包清单时终止导出。导出后生成 SHA-256，服务器部署前必须校验通过。

## 7. 服务器目录

```text
/opt/student-analysis/
├── releases/
│   ├── 2026.07.20-1/
│   └── 2026.08.01-1/
├── current -> releases/<当前版本>/
├── shared/
│   └── .env
└── backups/
```

- 每个版本使用独立目录和不可变版本号。
- `.env` 位于 `shared/`，仅服务器管理员可读。
- 数据库、上传和日志使用稳定的 Compose 项目名及命名卷，不随版本目录改变。
- `current` 仅在新版本验证通过后切换。

## 8. 首次部署流程

```bash
tar -xzf student-analysis-release-<version>.tar.gz
cd student-analysis-release-<version>
cp .env.example /opt/student-analysis/shared/.env
# 管理员填写密钥、数据库密码及 PROXY_NETWORK
./deploy.sh
```

`deploy.sh` 按顺序执行：

1. 校验发布包 SHA-256。
2. 检查 Docker、Compose、磁盘空间、`.env` 权限和必填配置。
3. 验证 `PROXY_NETWORK` 对应的外部 Docker 网络存在。
4. 构建带版本标签的 Web 镜像。
5. 启动 MySQL 并等待健康检查通过。
6. 幂等创建空数据库和表结构，不得清空已有数据。
7. 启动 Web 并等待 `/health` 通过。
8. 验证代理容器可解析并访问 `student-analysis-web:8000`。
9. 输出反向代理目标、容器状态和人工验收清单。

任何一步失败都必须返回非零退出码并指出失败阶段，不能用交互式“忽略错误继续”掩盖数据库或健康检查失败。

## 9. 升级与回滚

升级流程：

1. 创建新版本目录并校验发布包。
2. 自动备份 MySQL；备份失败则终止发布。
3. 构建新版本 Web 镜像。
4. 执行明确声明的兼容性数据库变更。
5. 重建 Web 并执行健康检查和页面冒烟测试。
6. 验证通过后更新 `current`。

应用发布失败时停止失败的新 Web 容器，使用上一版本镜像和配置重新创建 Web，保留 MySQL、上传和日志卷，并以 `/health` 通过作为回滚成功条件。

数据库回滚不自动执行。若未来升级包含不可逆变更，必须在发布说明中标记并通过指定备份人工恢复。本次首版部署不允许破坏性数据库迁移。

## 10. 备份与恢复

- 每次升级前执行 MySQL 逻辑备份。
- 推荐由服务器定时任务每日备份数据库和上传目录。
- 默认保留 7 个日备份和 4 个周备份；清理前验证目标位于 `/opt/student-analysis/backups/`。
- 备份文件仅允许服务器管理员读取。
- `restore.sh` 必须显式接收备份路径、验证文件完整性，并二次确认后才允许覆盖数据。
- 恢复后执行数据库健康检查、数据表检查和核心页面冒烟测试。

## 11. 日志与故障处理

- Web 和 MySQL 的主要日志写入标准输出，由 Docker 按大小和文件数量轮转。
- 应用文件日志仅作辅助，也必须轮转，避免再次产生超大日志。
- 启动失败、数据库不可达、导入失败和未处理异常记录清晰的时间、组件和错误摘要。
- 浏览器只返回通用错误页，不返回 Python 堆栈、SQL 或连接凭据。
- 部署文档提供查看容器状态、健康检查、最近日志、磁盘与卷状态的只读命令。

## 12. 验收标准

1. Web 和 MySQL 容器均健康。
2. 宿主机未公开应用端口和 MySQL `3306`，应用仅通过现有代理网络访问。
3. 代理容器可访问 `student-analysis-web:8000/health`；数据库异常时返回 503。
4. 校园网浏览器可打开首页、学生页、知识点页、预警页和导入页。
5. 使用脱敏小样本完成上传、导入、分析和页面查询。
6. 重启或重建 Web 后，数据库和上传文件仍然存在。
7. 模拟 Web 新版本启动失败后，可以恢复上一版本并通过健康检查。
8. 完成一次备份，并在隔离环境中验证其可恢复性。
9. 发布包不含学生原始数据、密钥、Git 历史、日志、备份和旧导出包。

## 13. 实施边界

下一阶段实施生产配置整改、健康检查、容器文件、发布/备份/恢复脚本、安全导出脚本和部署文档。

以下不在本次范围：修改现有反向代理产品、公网开放、域名和证书、登录与多角色权限、Kubernetes、多机高可用、Redis、Celery，以及迁移当前开发环境的学生数据。
