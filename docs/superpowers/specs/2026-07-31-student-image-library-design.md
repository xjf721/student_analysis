# 学生图像库与头像集成设计

## 1. 背景与目标

当前系统已具备学生基础信息、学生画像和学生数据全览，但学生模型与页面尚未包含照片。教师现有照片文件主要采用两种命名格式：

- `01-李少飞.jpg`：数字为该学生学号末两位。
- `202306142001江承阳.jpg`：开头数字为完整学号。

本功能新增班级隔离的学生图像库，实现照片批量上传、文件名自动解析、学生自动匹配、待处理照片人工调整，以及学生画像和数据全览中的头像展示。

目标如下：

1. 照片可先于学生数据上传，学生导入后自动补关联。
2. 所有自动匹配均严格限定在上传时选择的当前班级。
3. 同一学生只保留一张有效照片，新照片替换旧照片，不保留历史版本。
4. 支持从图像库选择头像或从本地单独上传；本地上传的照片立即进入图像库。
5. 照片文件、匹配规则和页面展示相互解耦，复杂逻辑进入 Service 层。

## 2. 非目标

本期不实现以下能力：

- 人脸识别、人脸相似度匹配或自动裁脸。
- 头像历史版本、回收站或版本恢复。
- 跨班级自动匹配和跨班级共享照片。
- 对象存储、CDN 或云端媒体服务。
- 学生自行登录上传头像。

## 3. 总体方案

采用“文件系统保存图片、MySQL 保存元数据”的方式。

```text
批量/单独上传
    ↓
StudentImageService 校验与标准化
    ↓
保存到 uploads/student_images/<class_id>/
    ↓
student_image 元数据入库
    ↓
按当前班级执行确定性匹配
    ├─ 唯一匹配 → 关联学生并成为头像
    ├─ 无匹配   → pending
    └─ 信息矛盾/多候选 → conflict
```

照片功能作为独立模块存在。Excel 导入器不解析图片，也不持有图片目录知识；学生导入完成后，仅由统一导入流程调用一次待处理照片重匹配服务。

## 4. 模块边界

### 4.1 数据模型

新增 `models/student_image.py`，只负责照片元数据和学生关联关系。

### 4.2 Repository

新增 `repositories/student_image_repo.py`，负责：

- 按班级、状态、学生和关键字查询。
- 创建、更新、绑定、解绑和删除照片元数据。
- 查询学生当前头像。
- 在事务中维护“一名学生最多一张照片”的约束。

### 4.3 Service

新增 `services/student_image_service.py`，负责：

- 上传文件校验和图片标准化。
- ZIP 安全解包和批次结果汇总。
- 文件名解析与姓名规范化。
- 班级内自动匹配和待处理照片重匹配。
- 单图替换、人工绑定、改绑和文件清理。
- 文件与数据库一致性补偿。

### 4.4 Controller

新增 `controllers/student_image_controller.py`，负责：

- 图像库页面和 JSON API。
- 获取当前班级并进行请求级权限校验。
- 参数校验、调用 Service 和转换 HTTP 响应。
- 通过受保护路由输出图片内容。

Controller 不实现文件名解析、学生匹配或替换算法。

### 4.5 现有模块改动

- `Student.to_dict()` 增加 `avatar_url`，无头像时为 `null`。
- `StudentRepository.get_full_overview()` 的 `basic` 增加 `avatar_url`。
- `controllers/__init__.py` 和 `app.py` 注册图像库蓝图。
- 导入流程在一个文件或一批文件成功保存学生后，调用 `StudentImageService.rematch_pending(class_id)`。
- 删除学生前解除头像关联，使图片返回当前班级的待关联区。

## 5. 数据模型

新增 `student_image` 表：

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `id` | Integer，主键 | 图片记录 ID |
| `class_id` | Integer，非空，外键 | 上传时所属班级，也是所有匹配和访问的隔离边界 |
| `student_id` | Integer，可空，唯一，外键 | 已关联学生；为空表示尚未关联 |
| `original_filename` | String(255)，非空 | 用户上传时的原始文件名，仅展示和审计使用 |
| `storage_filename` | String(255)，非空，唯一 | 系统生成的安全文件名 |
| `parsed_student_no` | String(50)，可空 | 从文件名提取的完整学号或两位尾号 |
| `number_match_type` | String(20)，可空 | `full` 或 `suffix` |
| `parsed_name` | String(100)，可空 | 从文件名提取并规范化后的姓名 |
| `match_status` | String(20)，非空 | `matched`、`pending` 或 `conflict` |
| `match_message` | String(255)，可空 | 未匹配、冲突或人工调整说明 |
| `mime_type` | String(50)，非空 | 标准化后文件 MIME 类型 |
| `file_size` | Integer，非空 | 标准化后文件大小 |
| `content_hash` | String(64)，非空 | SHA-256，用于识别重复图片 |
| `created_at` | DateTime | 创建时间 |
| `updated_at` | DateTime | 最近更新时间 |

约束与索引：

- `student_id` 唯一，保证每名学生最多关联一张照片；MySQL 允许多个 `NULL`，因此可保留多张待关联照片。
- 建立 `(class_id, match_status)`、`(class_id, parsed_name)` 和 `(class_id, parsed_student_no)` 索引。
- `class_id + content_hash` 用于同班级内重复图片检测。
- `match_status` 使用字符串而不是数据库 Enum，降低当前轻量 schema 升级方式的维护成本。

新表由现有 `db.create_all()` 创建，不需要向旧表追加字段。学生删除流程显式将关联照片的 `student_id` 置空并设为 `pending`，避免依赖不同数据库环境下的级联行为。

## 6. 文件存储与图片处理

存储根目录为：

```text
uploads/student_images/<class_id>/<uuid>.jpg
```

规则如下：

1. 磁盘文件名使用 UUID，不使用原始中文文件名，也不使用 `secure_filename()` 的结果进行业务匹配。
2. 原始文件名原样保存在数据库中，用于解析、展示和问题追踪。
3. 支持 JPG、JPEG、PNG 和 WebP；ZIP 只作为批量传输容器。
4. 使用 Pillow 读取并验证实际图片内容，不仅检查扩展名或客户端 MIME。
5. 应用 EXIF 方向纠正，按比例缩放，最长边不超过 1024 像素，再统一保存为 JPEG；不执行自动人脸裁切。
6. 单张原始图片上限 5 MB，单批最多 200 张；批量请求总上限调整为 100 MB。
7. ZIP 解包时拒绝绝对路径、`..` 路径穿越、嵌套压缩包和非支持文件。
8. 页面使用 `object-fit: cover` 在固定纵向区域展示，不修改源图片构图。

## 7. 文件名解析与自动匹配

### 7.1 姓名规范化

匹配前仅执行确定性规范化：去除首尾空白、移除姓名两侧的 `_`、`-` 和空格。不进行拼音、同音、模糊或包含关系匹配。

### 7.2 完整学号格式

文件名形式：

```text
202306142001江承阳.jpg
```

解析开头连续数字为完整学号，余下内容为姓名。匹配条件必须同时满足：

```text
Student.class_id == 当前班级
Student.student_no == 解析出的完整学号
Student.name == 规范化后的姓名
```

若学号找到但姓名不一致，状态为 `conflict`，不自动绑定。

### 7.3 学号末两位格式

文件名形式：

```text
01-李少飞.jpg
```

仅识别“两个数字 + 连字符 + 姓名”的明确格式。匹配条件必须同时满足：

```text
Student.class_id == 当前班级
Student.student_no 末两位 == 解析出的两位数字
Student.name == 规范化后的姓名
```

只有结果唯一时才自动绑定。其他班级的同名或同尾号学生完全不参与候选查询。

### 7.4 匹配状态

- `matched`：当前班级中存在唯一且全部字段一致的学生。
- `pending`：文件名可解析，但当前班级尚无符合条件的学生；学生后续导入后可重新匹配。
- `conflict`：存在多个候选，或学号信息与姓名信息矛盾，需要人工处理。
- 无法解析文件名但图片有效时，记录为 `pending`，并提示需要人工选择学生。
- 无法解码、超限或格式不支持的文件不进入图像库，仅出现在本批失败结果中。

## 8. 上传、替换与人工调整

### 8.1 批量上传

图像库页面默认继承当前活动班级。用户可多选图片或上传一个 ZIP。服务对每个文件独立处理，单个失败不回滚其他成功文件。

批次返回：

- 文件总数。
- 已自动关联数。
- 待关联数。
- 冲突数。
- 失败数。
- 每个文件的状态和具体原因。

### 8.2 新图替换旧图

同一学生已有头像时，新图通过全部校验后才开始替换：

1. 将新图写入同目录临时文件。
2. 开启数据库事务并更新学生图片元数据。
3. 原子移动新文件到最终路径。
4. 提交事务。
5. 删除旧文件。

若数据库操作或最终文件移动失败，删除临时文件并保留旧记录与旧照片。旧文件删除失败时记录错误日志，并由清理任务或人工维护处理，不回退已经可用的新头像。

同班级上传完全相同的 `content_hash` 时，不新增冗余记录，返回“重复图片”提示。

### 8.3 从图像库选择

学生画像和数据全览复用同一个选择弹窗，只显示当前班级的图像库内容，并支持按姓名、学号、原始文件名和状态筛选。

- 选择未关联图片：绑定到目标学生。
- 目标学生已有头像：二次确认后删除目标学生旧照片并完成替换。
- 选择已关联其他学生的图片：二次确认后改绑；原学生变为无头像。
- 所有绑定操作都再次校验图片和目标学生的 `class_id` 一致。

### 8.4 本地单独上传

从学生页面上传时，目标学生和当前班级由 URL 与服务端查询确定，不接受客户端提交任意班级。图片成功后立即进入图像库并成为该学生头像；已有头像按替换流程处理。

### 8.5 删除图片

图像库允许删除照片。删除已关联照片需二次确认；删除成功后学生恢复默认头像。数据库删除失败时保留文件，文件删除失败时记录日志并返回可操作的错误信息。

## 9. 学生导入后的自动关联

自动关联不放入具体的雨课堂或头歌导入器中。统一导入流程在本次导入成功保存学生后调用：

```python
StudentImageService.rematch_pending(class_id)
```

该方法只查询指定 `class_id` 下的 `pending` 和 `conflict` 照片，并使用与上传时完全相同的匹配器重新判断。这样可以保证：

- 不跨班级扫描。
- 不在每个学生保存时重复扫描照片。
- 新增其他平台导入器时无需复制头像逻辑。
- 重新匹配不会触发行为、知识或风险分析，也不会增加页面实时计算。

导入结果附加头像关联摘要，例如“自动关联 12 张，仍待处理 3 张”，但照片失败不回滚已成功导入的教学数据。

## 10. 页面设计

### 10.1 图像库页面

新增页面 `/student-images`，位于当前班级上下文中，包含：

- 当前班级选择/提示。
- 多文件上传和 ZIP 上传入口。
- 图像总数、已关联、待关联、冲突四个统计项。
- 姓名/学号/文件名搜索和状态筛选。
- 分页照片卡片，显示缩略图、解析信息、关联学生和状态。
- 待关联、处理冲突、更换绑定和删除操作。
- 上传后的逐文件结果弹窗。

列表默认每页 24 张，不一次加载全班原图；缩略图使用受保护图片接口并允许浏览器私有缓存。

### 10.2 学生画像页

在现有基础信息卡左侧加入 `132 × 166` 的纵向照片区，照片下方提供：

- “从图像库选择”。
- “本地上传”。

无照片时显示包含姓名首字的默认头像。现有雷达图、画像摘要和其他分析内容不改变。

### 10.3 学生数据全览页

基础信息区改为照片、学生信息、操作按钮三列布局。照片与画像页保持相同的 `132 × 166` 尺寸和纵向比例；窄屏时改为上下排列。下方知识点、作业和其他明细结构不改变。

“更换头像”复用画像页的选图/上传弹窗，避免形成两套交互逻辑。

## 11. API 设计

| 方法与路径 | 用途 |
| --- | --- |
| `GET /student-images` | 图像库页面 |
| `GET /api/student-images` | 当前班级照片分页、搜索与状态筛选 |
| `POST /api/student-images/batch` | 当前班级多图片或 ZIP 批量上传 |
| `POST /api/student-images/<image_id>/bind` | 将图像库图片绑定或改绑到当前班级学生 |
| `DELETE /api/student-images/<image_id>` | 删除当前班级图片 |
| `POST /api/student/<student_id>/image` | 为指定学生从本地单独上传并替换头像 |
| `GET /media/student-images/<image_id>` | 经登录和班级校验后读取图片 |

绑定接口请求体包含 `student_id` 和 `confirm_replace`。若目标已有头像或源图片已属于其他学生，而 `confirm_replace` 为 `false`，返回 HTTP 409 及明确的确认信息。

现有学生详情 API 和全览 API 返回 `avatar_url`，页面不自行拼接文件系统路径。

## 12. 权限、安全与隐私

1. 所有页面、API 和媒体读取路由都要求已登录并存在活动班级。
2. 图片、学生和活动班级的 `class_id` 必须一致，否则返回 404，避免暴露其他班级是否存在该资源。
3. 图片不放入公开 `static` 目录，也不直接暴露磁盘路径。
4. 下载响应使用正确 MIME、ETag 和 `Cache-Control: private`；不允许公开代理缓存。
5. 原始文件名仅作为文本展示，前端必须转义；磁盘路径永远由系统生成。
6. ZIP 条目数量、展开总大小和单文件大小均受限，防止压缩炸弹和路径穿越。
7. 日志不记录图片二进制，只记录班级 ID、记录 ID、原始文件名、处理状态和错误原因。

## 13. 错误处理与一致性

- 每个上传文件独立处理并返回明确结果。
- 批量上传中单文件失败不影响其他文件。
- 文件写入使用临时文件和原子重命名，避免页面读取半成品。
- 数据库事务失败时清理本次临时文件。
- 替换操作在新头像可用前不删除旧头像。
- 检测到数据库记录存在但磁盘文件缺失时，媒体接口返回默认头像并记录错误；图像库将该记录显示为异常，供教师重新上传或删除。
- 所有异常写入现有 `logs/system.log`。

## 14. 性能设计

- 图像库 API 必须分页，默认 24 张，最大 100 张。
- 列表只加载当前页缩略图，不一次加载全班原图。
- 图片上传时完成缩放和压缩，页面访问不实时处理图片。
- 学生导入后仅扫描当前班级待处理照片，不扫描全部班级或已匹配照片。
- `avatar_url` 只读取已持久化关联，不进行实时文件名匹配。

- 当前班级 + 学号末两位 + 姓名唯一匹配。

### 15.2 Service/Repository 测试

- 同一学生新图替换旧图，旧文件被清理且数据库只有一条关联。

- 人工绑定、替换和跨学生改绑行为。
- 删除学生后图片保留并回到当前班级待关联区。

- 无头像时两个页面显示默认头像。
- 画像页和全览页显示同尺寸照片，并可打开统一更换弹窗。
- 图像库分页、筛选、搜索和逐文件上传结果正确。

## 16. 验收标准

1. 在当前班级批量上传两种命名格式的照片后，唯一匹配照片自动成为对应学生头像。
2. `01-李少飞.jpg` 只在当前班级内按“学号末两位 + 姓名”匹配，其他班级不参与。
3. 先上传照片、后导入学生数据时，导入完成后照片能自动补关联。
4. 无法唯一匹配的照片可在图像库中查看原因并人工绑定。
5. 教师可在画像页和全览页从图像库选择，或从本地上传照片。
6. 本地上传照片立即进入图像库；同一学生的新照片替换旧照片且不保留历史版本。
7. 学生删除后照片仍保留在原班级图像库中并变为待关联。
8. 学生画像和数据全览都显示 `132 × 166` 的纵向照片；无照片时显示默认头像。
9. 未授权用户和其他班级无法读取或修改照片。
10. 图像库分页加载，页面访问不执行图片匹配或实时图片处理。
